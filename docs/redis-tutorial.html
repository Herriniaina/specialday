1C'est quoi, vraiment

Redis est un store clé-valeur en mémoire, à la base. Mais le réduire à "un cache" fait manquer l'essentiel : c'est surtout un serveur de structures de données distant — listes, sets, hash, sorted sets, streams — avec des opérations atomiques dessus, exécutées par un moteur mono-thread (pour la partie exécution des commandes).

Cette architecture mono-thread est la clé pour comprendre Redis : il n'y a pas de race condition entre deux commandes, chaque commande s'exécute jusqu'au bout avant la suivante. C'est ce qui rend Redis prévisible et rapide pour des opérations courtes, mais aussi ce qui le rend vulnérable à une seule commande lente qui bloque tout le serveur.

À retenir Redis n'est pas une base de données relationnelle réduite. C'est un outil pour des accès O(1)/O(log n) sur des structures en mémoire, avec de la persistance en option — pas pour des requêtes complexes ou des jointures.

3Persistance : RDB vs AOF

Redis est en mémoire, mais peut persister sur disque de deux façons, combinables :

RDB (snapshot)

Dump binaire complet à intervalles réguliers (SAVE / BGSAVE). Compact, rapide à recharger. Risque : perte de toutes les écritures depuis le dernier snapshot en cas de crash.

AOF (append-only file)

Journal de toutes les commandes d'écriture, rejouées au redémarrage. Plus durable (config appendfsync everysec ou always), mais fichier plus lourd et reload plus lent.

En pratique : si Redis est utilisé comme cache pur (données reconstructibles depuis une source de vérité), la persistance est secondaire, voire désactivable. S'il porte des données qu'on ne peut pas se permettre de perdre (queue de jobs, sessions critiques), il faut AOF avec un fsync agressif — ou ne pas utiliser Redis comme source de vérité pour ces données.

4TTL & éviction mémoire

Le TTL (EXPIRE, SET ... EX) est le mécanisme central pour un usage cache. Sans lui, Redis grossit indéfiniment.

Quand la mémoire max (maxmemory) est atteinte, la politique d'éviction (maxmemory-policy) décide quoi supprimer :

  • noeviction — refuse les écritures (défaut). Dangereux si non anticipé : l'appli casse au lieu de perdre des données silencieusement.
  • allkeys-lru / allkeys-lfu — supprime les clés les moins récemment/fréquemment utilisées, peu importe le TTL. Bon pour un cache pur.
  • volatile-lru / volatile-ttl — n'évince que les clés qui ont un TTL. Permet de mélanger cache et données persistantes dans la même instance sans risque pour ces dernières.
Règle senior Choisis la politique d'éviction avant la mise en prod, pas après un incident mémoire. noeviction + pas de maxmemory défini = crash OOM garanti à terme.

5Atomicité, transactions, Lua

Chaque commande individuelle est atomique. Pour enchaîner plusieurs opérations de façon atomique, trois outils :

  • MULTI/EXEC — met en file une séquence de commandes, exécutées d'un bloc. Pas de rollback si une commande échoue en cours de route (contrairement à une transaction SQL).
  • WATCH — verrouillage optimiste : annule le MULTI/EXEC si une clé surveillée a changé entre-temps.
  • Scripts Lua (EVAL) — exécutés atomiquement côté serveur, sans aller-retour réseau entre chaque étape. C'est l'outil pour de la logique conditionnelle complexe (ex: "décrémente un stock seulement si > 0").
-- Exemple : décrément conditionnel atomique via Lua
EVAL "if redis.call('GET', KEYS[1]) > 0 then return redis.call('DECR', KEYS[1]) else return -1 end" 1 stock:sku42

6Files de messages avec Redis

Trois façons de faire une queue, avec des garanties très différentes :

ApprocheGarantiesQuand l'utiliser
LPUSH / BRPOPAucune : si le consumer crash après BRPOP, le message est perduFire-and-forget, tolérant à la perte
Pub/SubAucune persistance : un message publié sans abonné connecté est perduNotifications temps réel, broadcast
Streams (XADD + consumer groups)At-least-once : un message n'est retiré qu'après XACK expliciteTraitement fiable de jobs, event sourcing

Le pattern Stream + consumer group ressemble à Kafka en plus léger :

XADD messages '*' payload '{"type":"welcome_email"}'
XREADGROUP GROUP symfony consumer-1 COUNT 1 STREAMS messages '>'
XACK messages symfony <message-id>

Si un consumer crash entre le XREADGROUP et le XACK, le message reste dans la pending entries list (PEL) du groupe — récupérable via XPENDING / XCLAIM par un autre consumer. C'est ce qui donne la garantie "at-least-once".

Piège At-least-once ≠ exactly-once. Si le traitement du message n'est pas idempotent (ex: envoyer un email deux fois), un redémarrage de worker au mauvais moment peut causer un traitement en double. Concevoir les handlers pour être idempotents.

7Pub/Sub vs Streams vs Listes — résumé mental

  • Pub/Sub = radio en direct. Rien n'est stocké, si personne n'écoute au moment de l'émission, c'est perdu.
  • Liste (LPUSH/BRPOP) = pile de post-its. Simple, mais un post-it pris par un worker qui crash est perdu.
  • Stream = journal d'événements avec accusés de réception. Le bon choix dès qu'on ne peut pas se permettre de perdre un message.

8Dans ce projet

Ce dépôt utilise déjà Redis comme transport Symfony Messenger (config/packages/messenger.yaml), via la DSN :

MESSENGER_TRANSPORT_DSN=redis://redis:6379/messages
Concrètement : Symfony Messenger utilise un Stream Redis nommé messages, avec un consumer group par défaut nommé symfony. Le service worker (défini dans compose.override.yaml) exécute en continu messenger:consume async, ce qui correspond à des appels répétés de XREADGROUP + XACK.

Pour inspecter la queue manuellement :

docker compose exec redis redis-cli XLEN messages
docker compose exec redis redis-cli XRANGE messages - + COUNT 20
docker compose exec redis redis-cli XINFO GROUPS messages
docker compose exec redis redis-cli XPENDING messages symfony

Les messages qui épuisent la stratégie de retry (DeadlineRetryStrategy) partent vers le transport failed — mais celui-ci est Doctrine, pas Redis (voir config/packages/messenger.yaml), donc consultable via bin/console messenger:failed:show.

9Pièges classiques

  • KEYS * en prod — parcourt tout l'espace de clés en bloquant le thread. Toujours utiliser SCAN (curseur, non-bloquant) à la place.
  • Big keys — une seule clé avec des millions d'éléments (list, hash, set) ralentit toute commande dessus, et complique la réplication/le resharding.
  • Pas de TTL par défaut — oublier l'expiration transforme le cache en fuite mémoire progressive.
  • Redis comme unique source de vérité — sans persistance robuste (AOF + réplication), une perte de l'instance = perte de données. Ne jamais y stocker ce qui n'existe nulle part ailleurs sans l'avoir décidé consciemment.
  • Latence réseau sous-estimée — chaque aller-retour compte quand on enchaîne des commandes en boucle depuis l'appli ; préférer le pipelining ou MGET/MSET pour grouper les appels.
  • Confondre expiration et éviction — une clé avec TTL expiré n'est pas forcément supprimée activement immédiatement (suppression lazy ou par cycle actif) ; ça ne remplace pas une vraie politique maxmemory-policy.

10Sécurité

  • Redis n'a historiquement aucune authentification par défaut. Toujours définir requirepass (ou utiliser ACL depuis Redis 6+ pour des permissions par utilisateur).
  • Ne jamais exposer le port 6379 directement sur internet — le binder sur une interface privée / réseau Docker interne, comme c'est déjà le cas ici (compose.yaml n'expose le port qu'en dev via l'override).
  • Activer TLS pour les connexions inter-services en prod si le réseau n'est pas déjà isolé/de confiance.
  • Désactiver ou renommer les commandes dangereuses en prod (FLUSHALL, FLUSHDB, CONFIG) via rename-command.

11Scaling & haute disponibilité

Réplication

Un primary + N replicas en lecture seule. Résout la charge en lecture, pas la disponibilité en écriture : si le primary tombe, il faut une bascule.

Sentinel

Surveille le primary et orchestre le failover automatique vers un replica. Bon pour la haute dispo sans sharding.

Cluster

Sharding automatique des clés sur plusieurs nœuds (16384 hash slots). Nécessaire quand un seul nœud ne suffit plus en volume/débit.

Limite structurelle

Le cluster distribue les clés, mais les opérations multi-clés (MGET, transactions) exigent que les clés soient sur le même slot (hash tags : {user123}:profile).

12Monitoring & debug

INFO                     # stats globales : mémoire, clients, réplication...
SLOWLOG GET 10          # dernières commandes lentes
MONITOR                  # stream en direct de toutes les commandes (jamais en prod à fort trafic)
redis-cli --latency      # mesure la latence réseau/serveur en continu
redis-cli --bigkeys      # scan pour repérer les clés volumineuses
Attention MONITOR a un coût de performance notable sur une instance très sollicitée — à réserver au debug ciblé, jamais en observabilité continue.
